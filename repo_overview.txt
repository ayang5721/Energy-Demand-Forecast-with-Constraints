# Project Analysis

## 1. Introduction

### 1.1 Project Summary

- Project name:
  - Energy Demand Forecast with Constraints.
  - Evidence: README.md.

- What the repo does:
  - Builds a 24-hour-ahead PJM electricity load forecasting pipeline.
  - Compares raw forecast accuracy before constraints.
  - Aggregates load-area forecasts to zone-level load.
  - Runs a synthetic constrained dispatch layer to measure operational consequences.

- Core idea:
  - Use hourly load and weather data at issue time t to predict load at t + 24 hours.
  - Then ask whether the forecast is useful after it is used to schedule generation.

- Main inputs:
  - Load data: data/hrl_load_metered.csv.
  - Weather data used by the pipeline: data/4_year_kentucky_weather_data.csv.

- Main outputs:
  - Forecast metrics: results/metrics/pre_constraint_layer_forecast_metrics.csv.
  - Forecast metrics by load area: results/metrics/pre_constraint_layer_forecast_metrics_by_load_area.csv.
  - Error by hour: results/metrics/pre_constraint_layer_error_by_hour.csv.
  - Dispatch metrics: results/metrics/post_constraint_layer_dispatch_metrics.csv.
  - Combined forecast/dispatch summary: results/metrics/pre_post_constraint_layer_summary.csv.
  - Prediction files under results/predictions/.
  - Figures under results/figures/.

- Models and systems used:
  - Persistence baseline.
  - OLS.
  - Ridge.
  - Lasso.
  - Explicit NumPy residual neural network.
  - Explicit NumPy residual neural network with weather features.
  - Synthetic greedy dispatch layer.
  - Evidence: src/models.py, src/run.py, src/constraints.py.

### 1.2 Problem and Importance

- Real-world problem:
  - Short-term electricity demand forecasting.
  - Forecast-to-decision evaluation for generation scheduling.

- Why it matters:
  - If demand is underpredicted, scheduled generation can fall short of true load.
  - If demand is overpredicted, generation can be over-scheduled.
  - In this repo, under-generation is penalized more heavily than over-generation, so the direction of forecast error matters.

- Who would care:
  - Grid operators.
  - Utilities.
  - Energy forecasters.
  - Researchers studying decision-focused forecasting.

- Exact task:
  - Forecasting / regression: predict hourly MW load 24 hours ahead.
  - Post-processing / decision analysis: run forecasts through a dispatch layer.

- System input:
  - Hourly rows with timestamp, zone, load_area, and MW load.
  - Hourly weather rows with temperature and relative humidity.

- System output:
  - Predicted load_mw for each zone/load-area and target timestamp.
  - Zone-level predicted load.
  - Scheduled generation, under/over-generation, costs, penalties, and regret.

- Main assumptions:
  - Forecast horizon is exactly 24 hours.
  - Historical weather at issue time is available.
  - One Kentucky weather file is used for all zones/load areas.
  - The dispatch fleet is synthetic, not a real PJM fleet.
  - Under-generation penalty is 500 dollars/MWh.
  - Over-generation penalty is 50 dollars/MWh.
  - The dispatch layer is a comparison tool, not a real grid operations simulator.

### 1.3 Motivation and Background

- Motivation:
  - A model with the best forecast error is not always the model with the best downstream operating cost.
  - The project tries to compare both forecasting accuracy and operational usefulness.

- Background needed:
  - Load is measured in MW.
  - A load area is a regional demand series inside a PJM zone.
  - A forecast at time t predicts demand at time t + 24 hours.
  - Dispatch means scheduling generation to meet demand.
  - Regret means the cost difference between forecast-based dispatch and oracle dispatch using true load.

- Baseline without the project:
  - Use persistence: predicted load at t + 24 equals load at t.
  - Evidence: predict_persistence() in src/models.py.

- What the project improves:
  - Adds linear models and residual neural networks.
  - Adds weather-aware features.
  - Adds a constraint layer so forecast errors are evaluated in an operational context.

  - Zones: AEP, AP, ATSI, CE, DEOK, EKPC, OVEC.

  - Target timestamp range: 2025-06-04 04:00 UTC to 2026-06-01 03:00 UTC.
  - Evidence: results/predictions/pre_constraint_layer_feature_data_snapshot.csv.

- Weather handling:
  - load_weather_data() reads the metadata-prefixed weather CSV and normalizes columns to timestamp_utc, temperature_c, humidity_pct.
  - filter_weather_to_load_range() restricts the four-year weather file to the current load-data window plus a 24-hour lookback.
  - Evidence: src/data.py.

- Unit of observation:
  - One row is one hourly load measurement for one zone/load-area pair.
  - One supervised example predicts that same zone/load-area load 24 hours later.

- Split:
  - Chronological by each zone/load-area series.
  - 70% train, 15% validation, 15% test.
  - Split rows: 62,256 train, 13,341 validation, 13,347 test.
  - All 11 series are represented in each split.
  - Evidence: src/split.py and saved feature snapshot.

- Preprocessing:
  - Parse UTC and EPT timestamps.
  - Rename mw to load_mw and mkt_region to market_region.
  - Convert MW and weather columns to numeric.
  - Convert is_verified to boolean.
  - Strip string columns.
  - Drop missing required rows.
  - Drop duplicate timestamp/zone/load_area rows.
  - Drop feature rows without complete lag, rolling, weather, or exact target values.
  - Evidence: src/data.py and src/features.py.

- Leakage checks:
  - Target is exact t + 24 load.
  - Load lags use times at or before t.
  - Weather features use issue-time weather and 24-hour-lag weather.
  - No target-time weather is used.
  - Chronological split avoids future leakage within each series.

## 4. Methods

### 4.1 Methods and Algorithms

- Persistence:
  - Prediction equals current load_mw.
  - Implemented in predict_persistence() in src/models.py.

- OLS:
  - Explicit least-squares linear regression using numpy.linalg.lstsq.
  - Implemented in LinearModel._fit_ols().

- Ridge:
  - Explicit L2-regularized linear regression.
  - Intercept is not penalized.
  - Implemented in LinearModel._fit_ridge().

- Lasso:
  - Explicit coordinate descent with soft-thresholding.
  - Implemented in LinearModel._fit_lasso().

- Base residual neural network:
  - Explicit NumPy MLP.
  - Hidden layers: 64 and 32 units.
  - ReLU hidden activations.
  - Linear output.
  - He initialization.
  - Mini-batch Adam optimizer.
  - L2 weight decay.
  - Internal validation split and early stopping.
  - Learns residual = target_load_mw - current load_mw.
  - Final prediction = current load_mw + predicted residual.
  - Implemented in ResidualNeuralNetworkModel in src/models.py.

- Weather residual neural network:
  - Same explicit residual MLP.
  - Uses base features plus temperature and humidity features.
  - Trained in src/run.py through train_neural_network() with WEATHER_FEATURE_COLUMNS.

- Constraint layer:
  - Load-area predictions are aggregated to zone-level load in src/operational.py.
  - create_generator_fleet() builds a synthetic fleet sized from observed peak zone load.
  - run_constrained_dispatch() greedily dispatches cheapest generators first.
  - It compares forecast-based scheduled generation to true load.
  - Under-generation and over-generation are soft penalties, not hard correction constraints.

- Dispatch assumptions:
  - cheap_base: 35% of max load at 25 dollars/MWh.
  - mid_cost: 35% at 50 dollars/MWh.
  - high_cost: 35% at 85 dollars/MWh.
  - peaker: 25% at 150 dollars/MWh.
  - Under-generation penalty: 500 dollars/MWh.
  - Over-generation penalty: 50 dollars/MWh.
  - Evidence: src/constraints.py.

### 4.2 Training Procedure

- Main training command:
  - .venv/bin/python -u src/run.py.
  - Evidence: README.md.

- Target:
  - target_load_mw, exact same-zone/load-area load at t + 24 hours.

- Training flow:
  - Load and clean load/weather data.
  - Create feature dataset.
  - Split per series chronologically.
  - Train Persistence, OLS, base NN, weather NN, Ridge, and Lasso.
  - Save predictions, metrics, plots, and dispatch outputs.
  - Evidence: src/run.py.

- Hyperparameters:
  - Ridge alpha grid: 0.01, 0.1, 1.0, 10.0, 100.0.
  - Best Ridge alpha in current saved validation results: 0.01.
  - Lasso alpha grid: 0.001, 0.01, 0.1, 1.0, 10.0, 100.0.
  - Best Lasso alpha in current saved validation results: 0.1.
  - NN hidden layers: (64, 32).
  - NN alpha: 0.01.
  - NN learning_rate_init: 0.0001.
  - NN batch_size: 128.
  - NN max_iter: 600.
  - NN random_state: 42.
  - NN validation_fraction: 0.10.
  - NN n_iter_no_change: 10.

- Cross-validation:
  - No k-fold cross-validation.
  - Ridge and Lasso use validation split for alpha tuning.
  - Neural-network hyperparameters are fixed manually.

- Reproducibility:
  - Random seed is set for the NumPy NN.
  - Data and outputs are present in repo.
  - Full data-source reproducibility is limited because dataset download citations are missing.

## 5. Experiments / Results / Discussion

### 5.1 Evaluation Metrics

- Forecast metrics:
  - MAE.
  - RMSE.
  - MAPE.
  - Bias.
  - Evidence: src/evaluate.py and results/metrics/pre_constraint_layer_forecast_metrics.csv.

- Why these metrics matter:
  - MAE: typical absolute MW error.
  - RMSE: emphasizes large misses.
  - MAPE: percent error, but can be misleading for small loads.
  - Bias: systematic over- or underprediction.

- Operational metrics:
  - Under-generation rate and MWh.

  - Penalty cost.

  - Evidence: src/constraints.py and results/metrics/pre_post_constraint_layer_summary.csv.

- Most important metric by project goal:
  - For pure forecasting: RMSE, MAE, and bias are most important.
  - For constrained dispatch: total constraint regret is the most important final metric, with MAE/RMSE/bias as sanity checks.

### 5.3 Results

- Current forecast results from results/metrics/pre_constraint_layer_forecast_metrics.csv:
  - Persistence: MAE 235.361, RMSE 434.434, MAPE 7.694%, Bias -0.546.
  - OLS: MAE 250.260, RMSE 404.006, MAPE 34.996%, Bias 111.262.
  - Neural Network: MAE 209.741, RMSE 367.962, MAPE 16.715%, Bias 59.465.
  - Neural Network + Weather: MAE 213.052, RMSE 357.440, MAPE 22.422%, Bias 17.807.
  - Ridge: MAE 250.260, RMSE 404.005, MAPE 34.996%, Bias 111.259.
  - Lasso: MAE 249.018, RMSE 403.082, MAPE 34.886%, Bias 106.671.

- Best forecast metric winners:
  - Best MAE: Neural Network.
  - Best RMSE: Neural Network + Weather.
  - Best MAPE: Persistence.
  - Lowest bias magnitude: Persistence.
  - Lowest non-persistence bias magnitude: Neural Network + Weather.

- Current post-constraint results from results/metrics/pre_post_constraint_layer_summary.csv:
  - Lowest total operational cost: OLS, about 2.205B dollars.
  - Lowest total constraint regret: OLS, about 564.431M dollars.
  - Ridge is nearly tied with OLS on regret, about 564.435M dollars.
  - Lasso is next, about 569.840M dollars.
  - Base NN regret: about 576.252M dollars.
  - Weather NN regret: about 658.618M dollars.
  - Persistence regret: about 836.108M dollars.

- Main result:
  - The neural networks are currently the best forecasters by MAE/RMSE.
  - OLS/Ridge/Lasso are currently better under the synthetic dispatch regret metric.
  - This creates a real forecast-vs-decision tradeoff.

- Important comparison:
  - Weather NN improves RMSE over base NN by about 10.52 MW and reduces bias magnitude from 59.47 MW to 17.81 MW.
  - But weather NN increases regret from about 576.25M to 658.62M dollars under the current synthetic dispatch assumptions.
  - This means better forecast metrics do not automatically mean lower dispatch regret.

### 5.4 Discussion and Error Analysis

- Interpretation:
  - Base NN is the strongest model by MAE.
  - Weather NN is the strongest model by RMSE and non-persistence bias.
  - OLS/Ridge/Lasso perform worse as forecasters but have lower regret because their positive bias reduces expensive under-generation under the repo's asymmetric penalty setup.

- Why MAPE is tricky:
  - Persistence has the best MAPE.
  - Linear models have very high MAPE, likely influenced by small-load series where percentage error becomes large.
  - MAPE should not be the lead metric for dispatch decisions.

- Why regret can disagree with error:
  - The constraint layer strongly penalizes under-generation.
  - A positively biased model can look operationally better because it over-schedules more often.
  - That may be useful under this synthetic cost model, but it may not generalize to real dispatch.

- Overfitting / underfitting:
  - Not enough evidence in repo to diagnose fully.
  - Missing train curves, validation curves, and repeated NN seed results.
  - The explicit NumPy NN stores loss_curve_ and validation_loss_curve_, but src/run.py does not save those curves.

- Error-analysis files:
  - results/metrics/pre_constraint_layer_error_by_hour.csv.
  - results/metrics/pre_constraint_layer_forecast_metrics_by_load_area.csv.
  - results/figures/pre_constraint_error/pre_constraint_layer_error_by_hour.png.
  - results/figures/pre_constraint_load_area/.

- Constraint limitation:
  - The dispatch layer is intentionally simplified.
  - It does not include ramping, unit commitment, reserves, outage modeling, transmission, real bids, or real generator data.

## 6. Conclusion / Future Work

### 6.1 Conclusion

- What the repo accomplished:
  - Built a full PJM load forecasting pipeline.
  - Added explicit residual NumPy neural networks.
  - Added weather features.
  - Evaluated both forecast error and downstream constrained-dispatch regret.

- Strongest forecast result:
  - Base NN has the lowest MAE.
  - Weather NN has the lowest RMSE and much lower non-persistence bias.

- Strongest constrained-dispatch result:
  - OLS has the lowest total operational cost and constraint regret in the current saved run.
  - Ridge is almost tied with OLS.

- Main lesson:
  - The best forecaster and the best dispatch-regret model are not the same.
  - The NN models are more accurate, but the synthetic constraint layer favors the more positively biased linear models.

- Claims supported:
  - Neural networks improve MAE/RMSE over persistence and linear models in the current saved run.
  - Weather improves NN RMSE and bias but not regret.
  - Forecast accuracy and constraint regret can disagree.

- Claims not fully supported:
  - Real-world PJM operational cost claims.
  - General superiority of any model without penalty/fleet sensitivity tests.
  - Weather benefit beyond this one saved run.
